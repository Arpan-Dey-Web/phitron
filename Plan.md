# 4. How I Should Solve Problems

Never make this the routine:

`Read problem → look at solution → copy code`

Instead:

### Step 1 — Understand
- What is the input?
- What is the output?
- What are the constraints?
- What are the edge cases?

### Step 2 — Think
- Can I solve it with brute force?
- Why is brute force too slow?
- What information am I repeatedly calculating?
- Can a data structure reduce the work?

### Step 3 — Explain
Before coding, say:

> "I will use ___ because ___."

### Step 4 — Code
Write clean C++.

### Step 5 — Test
Check:
- Empty/small input
- Duplicate values
- Large values
- Boundary cases
- Minimum/maximum constraints

### Step 6 — Complexity
Always state:

`Time: O(?)`

`Space: O(?)`

### Step 7 — Review
Ask:

> "What clue in the problem should help me recognize this pattern next time?"

---

# 5. Editorial Rule

Do not open the editorial immediately.

For a normal problem:

- Think seriously for **20–30 minutes**
- Try at least one approach
- Write down what you know
- Then use a hint/editorial if necessary

After reading the solution:

> **Close it and code the solution yourself.**

Never copy-paste the final code and consider the problem solved.

---

# 6. Re-Solving Rule

Important problems must be solved again.

### Review cycle

- **First solve:** Today
- **Second solve:** 2–3 days later
- **Third solve:** 1–2 weeks later
- **Fourth solve:** 1–2 months later

This is how patterns become automatic.

# 16. Interview Communication Framework

Starting from Week 10, use this during coding practice:

### 1. Clarify
"Let me confirm the constraints and expected output."

### 2. Brute Force
"The straightforward approach would be..."

### 3. Problem With Brute Force
"However, this would take O(...)."

### 4. Optimization
"We can improve this using..."

### 5. Walk Through Example
"For this example..."

### 6. Code
Write the solution.

### 7. Test
"Let's test the edge cases."

### 8. Complexity
"Time complexity is O(...), space complexity is O(...)."
